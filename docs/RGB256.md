# C64RGB 256 - recolour packs for old 16-colour games (Fix 60)

(c) 2026 Mong00se

Octophonic's own games already have 256 colours. C64RGB 256 is for the OLD games: the same game, the
same pixels, new colours. It is a second core built from the same source as the Octophonic core
(`define RGB256`), shipped inside the Octophonic build and hidden on the card as
`_Computer/.C64RGB256_<date>.rbf` (a dot name - the MiSTer menu never lists it).

## How it works from your side

1. Put a pack beside the game, with the same name: `Games/Mygame.crt` and `Games/Mygame.rgb`
   (works for .prg, .crt, .d64, .g64, .t64, .d81).
2. Pick the game in Octophonic's browser as usual. Main sees the `.rgb`, starts the C64RGB 256 core
   with the pack and the game (2-3 s of blank screen - that is the core loading), and the game runs
   in the pack's first palette.
3. **SHIFT+F3** (held) - the next palette: 1, 2, ... the pack's last, Off (the stock colours), 1 ...
   The OSD's `Recolour` line shows which one, and you can set it there too (it is kept with the core's
   settings).
4. **SHIFT+F1** (held) - back to the Octophonic core and its KERNAL start screen. CTRL+F12 does the same.
   Picking a game WITHOUT a pack while in C64RGB 256 also goes back to the Octophonic core with that game.

Without Octophonic Main (no OS on the card), SHIFT+F1 just resets the C64 after about 4 seconds.

What C64RGB 256 keeps: the C64, 2 SIDs, the REU, the hot keys, Exact 50 Hz, fast load, the Octophonic
KERNAL and OS. It drops the Sound Expander (OPL2) to make room for the recolour unit.

## Level 1: what a pack can do

Each pixel's new colour depends only on what the core knows while drawing it:

- its C64 colour (0-15),
- the raster line (up to 16 line bands - gradients down the screen),
- where it is on the 40x25 screen (an area of cells) OR the char code under it (up to 13 such classes),
- which sprite drew it (each of the 8 its own colours), or that it is the border.

So a pack can never move or redraw a pixel - that is Level 2 (redrawn graphics by pattern), later.
A pack holds up to 8 palettes and 256 different colours.

## Making a pack in minutes (tools/rgb256/rgb256.py)

```
python3 tools/rgb256/rgb256.py grab mygame.crt --frames 3000,4500 --out mygame
python3 tools/rgb256/rgb256.py starter mygame.tags > mygame.txt
#   ... edit mygame.txt ...
python3 tools/rgb256/rgb256.py preview mygame.txt mygame.tags      # mygame_preview.png: before | each palette
python3 tools/rgb256/rgb256.py make mygame.txt                     # mygame.rgb - put it beside the game
```

`grab` runs the game in the Octophonic emulator (OCTO_TAGDUMP, `tools/rgb256/emulator-rgb256.patch`)
and keeps what the VIC drew - each pixel's colour, char code or sprite - plus gridded PNGs (raster lines,
the 40x25 cells, sprite numbers) to read the numbers off. `--joy "frame:bits,..."` presses the joystick
to get past a title screen. Plain screenshots (320x200, 384x272, 396x284) work too, without the char and
sprite information. `starter` writes a description with three palettes from the colours the game uses.
With OCTO_RGBPACK=mygame.rgb the emulator shows the pack live.

## The description (.txt)

```
name: Mygame
palettes: Day, Dusk, Night            # up to 8

[everywhere]                          # every pixel of these colours
blue      = #2a50d8 | #5a3a9a | #102050          # one value per palette, | between them
white     = same    | #fff0d0 | #c0d0ff          # same = the stock colour

[lines 51-130]                        # raster lines (the 25 rows are lines 51-250)
lightblue = #b8e0ff .. #5a8cf0 | ...             # a .. b: a gradient over the range

[area cols 0-39 rows 0-1]             # an area of the 40x25 screen (a score panel, say)
[chars 128-255]                       # these char codes (a game's walls, say)
[outside]                             # outside the 25 rows (an opened border)
[sprite 0]   [sprites 1-7]            # sprites by number
[border lines 0-311]                  # the border
```

- Colours by name (`black white red cyan purple green blue yellow orange brown lightred darkgrey grey
  lightgreen lightblue lightgrey`) or 0-15; several at once: `blue, lightblue = ...`.
- Values: `#rrggbb`, `r,g,b`, a C64 colour name, or `same`.
- Later sections win over earlier ones. `[lines ...]` can be combined with an area, chars or the border
  (`[area cols 0-39 rows 0-1 lines 51-60]`); sprites ignore line ranges.
- A section is an area OR chars, not both. Area beats chars where both apply to a cell.
- Limits: 16 line bands (each `[lines]` start/end is a cut; gradients share the spare bands), 13
  areas/char sets, 256 colours over all palettes (the tool rounds them if there are more, and says so).

`tools/rgb256/example.txt` uses every kind of section.

## The pack file (.rgb) - 14336 bytes ($3800)

| Offset  | Size | What |
|---------|------|------|
| `$0000` | 8    | `RGB256PK` (the magic) |
| `$0008` | 1    | version (1) |
| `$0009` | 1    | how many palettes (1-8) |
| `$0010` | 8x16 | palette names (ASCII, 0-padded) |
| `$0090` | 32   | title |
| `$00C0` | 64   | copyright text |
| `$0100` | 512  | line table: the band (0-15) of each raster line 0-511 |
| `$0300` | 256  | char table: the class (0-13, 0 = none) of each char code |
| `$0400` | 1024 | cell table: the class of each cell (row*40+column, 0-999); entry 1000 = outside the window |
| `$0800` | 4096 | remap: `group*16 + C64 colour` -> slot (0-255) |
| `$1800` | 8192 | palettes: 8 x 256 slots x (R, G, B, 0) |

For each pixel (rtl/rgb256.sv, three clocks of pipeline - under one pixel):

```
class = cell table[cell] if not 0, else char table[char code]     (graphics pixels; 13 at most)
group = sprite n: $F0+n    border: $E0+band    graphics: class*16+band     (band = line table[line])
slot  = remap[group*16 + colour]
RGB   = palette[p][slot]
```

The pack loads over the core's file index 4 (OSD: `Load Recolour Pack`, or Main with the game). A
pack that is short or has the wrong magic is not used (the picture stays stock).

## Proof

- `sim/rgb256/run.sh` - the RTL in Verilator against the tool's model, every pixel of tagged VIC-II
  frames and every palette, and that each pixel holds steady for its 4 clocks. `RGB256_SIM_OK`.
  Runs in the core build (GitHub Actions) on every commit; `run.sh PACK.rgb FRAMES.tags` for real frames.

## Level 2 (later)

Redrawn graphics by pattern: match an 8x8 char (or a sprite's bytes) and draw new pixels in its place.
The tag the VIC gives the recolour unit already has the char code and sprite number; Level 2 adds the
char's row and the pattern bytes, and a pattern table in the pack (a version 2 header).
