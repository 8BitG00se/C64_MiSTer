# C64RGB 256 - recolour packs for old 16-colour games (Fix 60)

(c) 2026 Mong00se

Octophonic's own games already have 256 colours. C64RGB 256 is for the OLD games: the same game, the
same pixels, new colours. It is a second core built from the same source as the Octophonic core
(`define RGB256`), shipped inside the Octophonic build and hidden on the card as
`_Computer/.C64RGB256_<date>.rbf` (a dot name - the MiSTer menu never lists it).

## How it works from your side

1. Put a pack beside the game, with the same name: `Games/Mygame.crt` and `Games/Mygame.rgb`
   (works for .prg, .crt, .d64, .g64, .t64, .d81).
2. Pick the game in Octophonic's browser as usual. Main sees the `.rgb`, starts the C64RGB 256 core
   with the pack and the game (2-3 s of blank screen - that is the core loading), and the game runs
   in the pack's first palette.
3. **SHIFT+F3** (held) - the next palette: 1, 2, ... the pack's last, Off (the stock colours), 1 ...
   The OSD's `Recolour` line shows which one, and you can set it there too (it is kept with the core's
   settings).
4. **SHIFT+F1** (held) - back to the Octophonic core and its KERNAL start screen. CTRL+F12 does the same.
   Picking a game WITHOUT a pack while in C64RGB 256 also goes back to the Octophonic core with that game.

Without Octophonic Main (no OS on the card), SHIFT+F1 just resets the C64 after about 4 seconds.

What C64RGB 256 keeps: the C64, 2 SIDs, the REU, the hot keys, Exact 50 Hz, fast load, the Octophonic
KERNAL and OS. It drops the Sound Expander (OPL2) to make room for the recolour unit.

## Level 1: what a pack can do

Each pixel's new colour depends only on what the core knows while drawing it:

- its C64 colour (0-15),
- the raster line (up to 16 line bands - gradients down the screen),
- where it is on the 40x25 screen (an area of cells) OR the char code under it (up to 13 such classes),
- which sprite drew it (each of the 8 its own colours), or that it is the border.

So a pack can never move or redraw a pixel - that is Level 2 (redrawn graphics by pattern), later.
A pack holds up to 8 palettes and 256 different colours.

## Making a pack in minutes (tools/rgb256/rgb256.py)

```
python3 tools/rgb256/rgb256.py grab mygame.crt --frames 3000,4500 --out mygame
python3 tools/rgb256/rgb256.py starter mygame.tags > mygame.txt
#   ... edit mygame.txt ...
python3 tools/rgb256/rgb256.py preview mygame.txt mygame.tags      # mygame_preview.png: before | each palette
python3 tools/rgb256/rgb256.py make mygame.txt                     # mygame.rgb - put it beside the game
```

`grab` runs the game in the Octophonic emulator (OCTO_TAGDUMP, `tools/rgb256/emulator-rgb256.patch`)
and keeps what the VIC drew - each pixel's colour, char code or sprite - plus gridded PNGs (raster lines,
the 40x25 cells, sprite numbers) to read the numbers off. `--joy "frame:bits,..."` presses the joystick
to get past a title screen. Plain screenshots (320x200, 384x272, 396x284) work too, without the char and
sprite information. `starter` writes a description with three palettes from the colours the game uses.
With OCTO_RGBPACK=mygame.rgb the emulator shows the pack live.

## The description (.txt)

```
name: Mygame
palettes: Day, Dusk, Night            # up to 8

[everywhere]                          # every pixel of these colours
blue      = #2a50d8 | #5a3a9a | #102050          # one value per palette, | between them
white     = same    | #fff0d0 | #c0d0ff          # same = the stock colour

[lines 51-130]                        # raster lines (the 25 rows are lines 51-250)
lightblue = #b8e0ff .. #5a8cf0 | ...             # a .. b: a gradient over the range

[area cols 0-39 rows 0-1]             # an area of the 40x25 screen (a score panel, say)
[chars 128-255]                       # these char codes (a game's walls, say)
[outside]                             # outside the 25 rows (an opened border)
[sprite 0]   [sprites 1-7]            # sprites by number
[border lines 0-311]                  # the border
```

- Colours by name (`black white red cyan purple green blue yellow orange brown lightred darkgrey grey
  lightgreen lightblue lightgrey`) or 0-15; several at once: `blue, lightblue = ...`.
- Values: `#rrggbb`, `r,g,b`, a C64 colour name, or `same`.
- Later sections win over earlier ones. `[lines ...]` can be combined with an area, chars or the border
  (`[area cols 0-39 rows 0-1 lines 51-60]`); sprites ignore line ranges.
- A section is an area OR chars, not both. Area beats chars where both apply to a cell.
- Limits: 16 line bands (each `[lines]` start/end is a cut; gradients share the spare bands), 13
  areas/char sets, 256 colours over all palettes (the tool rounds them if there are more, and says so).

`tools/rgb256/example.txt` uses every kind of section.

## The pack file (.rgb) - 14336 bytes ($3800)

| Offset  | Size | What |
|---------|------|------|
| `$0000` | 8    | `RGB256PK` (the magic) |
| `$0008` | 1    | version (1) |
| `$0009` | 1    | how many palettes (1-8) |
| `$0010` | 8x16 | palette names (ASCII, 0-padded) |
| `$0090` | 32   | title |
| `$00C0` | 64   | copyright text |
| `$0100` | 512  | line table: the band (0-15) of each raster line 0-511 |
| `$0300` | 256  | char table: the class (0-13, 0 = none) of each char code |
| `$0400` | 1024 | cell table: the class of each cell (row*40+column, 0-999); entry 1000 = outside the window |
| `$0800` | 4096 | remap: `group*16 + C64 colour` -> slot (0-255) |
| `$1800` | 8192 | palettes: 8 x 256 slots x (R, G, B, 0) |

For each pixel (rtl/rgb256.sv, three clocks of pipeline - under one pixel):

```
class = cell table[cell] if not 0, else char table[char code]     (graphics pixels; 13 at most)
group = sprite n: $F0+n    border: $E0+band    graphics: class*16+band     (band = line table[line])
slot  = remap[group*16 + colour]
RGB   = palette[p][slot]
```

The pack loads over the core's file index 4 (OSD: `Load Recolour Pack`, or Main with the game). A
pack that is short or has the wrong magic is not used (the picture stays stock).

## Proof

- `sim/rgb256/run.sh` - the RTL in Verilator against the tool's model, every pixel of tagged VIC-II
  frames and every palette, and that each pixel holds steady for its 4 clocks. `RGB256_SIM_OK`.
  Runs in the core build (GitHub Actions) on every commit; `run.sh PACK.rgb FRAMES.tags` for real frames.

## Level 2 (Build 14, pack version 2): redrawn blocks and sprites

Level 2 swaps what the VIC drew for the pack's own pixels, at the C64's own pixel grid (320x200 cells,
24x21 sprites - a fat multicolour pixel is two equal bytes), each pixel one of the pack's 256 colours.
Level 1 goes on working underneath: wherever Level 2 has nothing (a miss, or a 0 byte in the art) the pixel
is the Level 1 colour, as in Build 12.

Keys: **WIN+F4** Level 2 on/off (before/after; Level 1 stays), **WIN+F6** learn mode on/off.

### How the core does it

- The picture leaves the core 16 raster lines late (sound is not delayed: 1 ms). In those lines the core
  sees a whole 8x8 cell as the VIC drew it, fingerprints it, looks it up and fetches its art.
- The pack is copied by Main into the DDR3 (the whole file, at byte address `$34000000`); the core reads
  buckets from there. The first `$3800` bytes also go in over the loader as before (Level 1).

### The file

Bytes `$0000-$37FF` are a version 1 pack, with the version byte (`$0008`) = 2. Everything is little-endian.
Every offset is from the start of the file and a multiple of 8.

| Offset  | Size | What |
|---------|------|------|
| `$3800` | 4    | `LVL2` |
| `$3804` | 4    | 0 (flags, for later) |
| `$3808` | 4    | offset of the block table |
| `$380C` | 4    | NB: the block table has 2^NB buckets (0-20) |
| `$3810` | 4    | offset of the sprite table |
| `$3814` | 4    | NS: the sprite table has 2^NS buckets (0-16) |
| `$3818` | 4    | offset of the border table (0: none) |
| `$381C` | 4    | the file's length |
| `$3820` | 4    | how many blocks are in the table (for tools) |
| `$3824` | 4    | how many sprite frames (for tools) |
| `$3828` | 24   | 0 |
| `$3840` | 512  | the border table: for each raster line 0-511 a palette slot for the border (0: Level 1's) |
| `$3A40` | 144 x 2^NB | the block table |
| after it | 1024 x 2^NS | the sprite table |

(The tool writes them in that order; the core goes by the offsets.)

**Block table.** A bucket is 144 bytes: two entries of 72. An entry is the key (8 bytes, 0 = empty) and
the tile (64 bytes: row 0 first, left pixel first; each byte a palette slot, 0 = "not redrawn here").
A block's bucket is `key & (2^NB - 1)`; it may sit in either entry. If both are taken by other keys the
tool makes the table bigger (NB+1) and starts again. Keep it under a quarter full, NB at least 10.

**Sprite table.** A bucket is 1024 bytes: two entries of 512. An entry is the key (8 bytes, 0 = empty) and
the frame (504 bytes: 21 rows of 24, top row first, left pixel first; a palette slot, 0 = transparent).
Bucket `key & (2^NS - 1)`, either entry, grown the same way. NS at least 4.

A key that works out as 0 cannot be stored (it never happens in practice: 1 in 2^64).

### The key (one function for both)

CRC-64 with the polynomial `$42F0E1EBA9EA3693`, start value all ones, most significant bit first, nothing
reflected, no final XOR:

```
def key(data):
    crc = 0xFFFFFFFFFFFFFFFF
    for b in data:
        crc ^= b << 56
        for _ in range(8):
            crc = ((crc << 1) ^ 0x42F0E1EBA9EA3693 if crc >> 63 else crc << 1) & 0xFFFFFFFFFFFFFFFF
    return crc
key(b"123456789") == 0x9D13A61C0E5B0FF5        key(bytes(32)) == 0xCF3354C179E0A56C
```

**A block's key** is made from the 64 pixels of the cell in the VIC's *graphics layer*: the colour
(0-15) each pixel has before sprites and the border are put over it - whatever the mode (chars,
multicolour, bitmap, ECM), the bank or the charset. 32 bytes: rows top to bottom, in a row
`(pixel0 << 4) | pixel1`, `(pixel2 << 4) | pixel3` ... So two cells that look the same are the same
block, and a cell that changes colour is another block.

A cell is the 8 pixels the VIC shifts out for one of its 40 columns, on the 8 lines of one text row
(row counter 0-7). It moves with the scroll registers: with `XSCROLL` = x and the first line of a row
at raster line y, column c's pixel i on row line j is at window pixel `(8c + i + x, …)` on raster line
`y + j` (tag X = 32 + 8c + i + x). Only whole cells count: a row cut short (fewer than 8 lines), or
drawn in idle state, is not looked up. The cells are looked up under the border too.

**A sprite's key** is made from 67 bytes: `mc` (1 if the sprite is multicolour, else 0), its colour
(`$D027+n`, 0-15), then `$D025` and `$D026` (0-15 each; both 0 if not multicolour), then the 63 bytes of
its data block in RAM (`VIC bank + pointer*64`), as they are when the sprite's display starts (the
line before its first line). Sprite data in the character ROM is not matched.

### What a pixel shows (the model - rtl/remaster.sv and tools/rgb256 must agree, pixel for pixel)

For the pixel at tag X `R` on raster line `y`; `L1(colour, kind, code)` is the Level 1 colour:

```
blank                      -> black
border                     -> the border table[y] if not 0, else L1(border colour)
else:
  under = tile[j*8+i] of the pixel's cell, if the cell's block is in the table and that byte is not 0
          else L1(graphics layer colour, graphics, char code)
  for n = 0..7:                                      (sprite 0 is in front, as on the C64)
     sprite n is shown on this line, its frame is in the table, 0 <= col < 24 where
     col = (R - (X_n + 8)) >> (1 if X-expanded), f = frame[row*24 + col] is not 0,
     and (sprite n is in front of graphics ($D01B bit clear) or the graphics pixel is background)
     and (the VIC's pixel here is not a sprite, or is a sprite whose frame is in the table, or is sprite m > n)
        -> f, done
  the VIC's pixel is sprite m:  m's frame in the table -> under      (its redrawn frame is transparent here)
                                else -> L1(sprite colour, sprite m)  (a sprite with no art is the VIC's)
  else -> under
```

- "graphics pixel is background": the VIC's own foreground bit (the pattern bit, or the high bit of a
  multicolour pair) - the original graphics, not the tile.
- `row` 0-20 is the sprite data row the VIC shows on that line (Y expansion repeats rows); `X_n` is the
  sprite's X register (0-511). A sprite's first line is raster line `Y + 1`.
- Collisions and everything else the game can read stay the VIC's: Level 2 only changes what is shown.
- With Level 2 off (WIN+F4), or a pack without `LVL2`, the picture is Level 1's exactly.

### Learn mode (WIN+F6) and the .learn file

With learn mode on, each block or sprite frame the core looks up and does NOT find is written once to a
log in the DDR3 (and marked in the DDR3's copy of the table as "seen, no art", so it is logged once;
if its bucket is full it is skipped). Main saves the log beside the game as `<game>.learn` (and adds
to a .learn already there, each key once). With no version 2 pack Main puts an empty table in the
DDR3 (NB 13, NS 8) so learning works for any game. Baking art from a .learn is the PC tool's job
(tools/rgb256) in this build - not done on the machine.

`<game>.learn`: `RGBLEARN` (8 bytes), u32 version (2), u32 count, then count records of 80 bytes:

| Offset | Size | What |
|--------|------|------|
| 0      | 1    | 1 = block, 2 = sprite |
| 1      | 3    | 0 |
| 4      | 4    | sprite: mc, colour, `$D025`, `$D026` (the first 4 bytes of its key data); block: 0 |
| 8      | 8    | the key |
| 16     | 64   | block: the 32 key bytes, then 32 x 0; sprite: its 63 data bytes, then 0 |

(The tool should check that the key of a record's data is the record's key, and drop any that is not.)

In the DDR3 the log is at byte `$36000000`: `LRN2` and a u32 count, then the records from byte 8.

### Frames for the simulation (.l2f) - what `rgb256.py grab` writes for Level 2

One frame after another, each:

| Size | What |
|------|------|
| 32   | `L2F1`, u32 frame number, u32 W, u32 H, u32 first raster line, u32 tag X of the window's first pixel (32), u32 0, u32 0 |
| W x H | the VIC's colour index of each pixel (as .tags) |
| 2 x W x H | the tags (as .tags: kind << 8 or-ed with the code; kind 0 graphics, 1 sprite, 2 border, 3 blank) |
| W x H | the graphics layer: bits 3-0 the colour, bit 4 the foreground bit |
| W x H | the cell: `$FF` not in a cell, else bits 5-3 the row line j, bits 2-0 the pixel i (the column is counted: each i = 0 starts the next) |
| 96 x H | for each line, 8 sprites x 12 bytes: flags (b0 shown on this line, b1 X-expanded, b2 behind graphics, b3 multicolour, b4 its display starts on this line), row (0-20), X (u16), colour, `$D025`, `$D026`, 0, the data block's RAM address (u16), 0, 0 |
| 65536 | the C64's RAM at the end of the frame |

The model's answer for a frame is W x H x 3 bytes of RGB (`rgb256.py l2model PACK FRAMES.l2f OUT.rgb [palette]`);
`sim/remaster/run.sh PACK FRAMES.l2f` plays the frames through the RTL and compares every pixel.
