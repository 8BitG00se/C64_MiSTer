# OctoPaint build 1 - the build spec

Original project by Mong00se (Octophonic 64). A paint program for the Octophonic 64, written in
6502 (ACME), running on OctoVIC. Build 1 is a `.prg` only. A Windows version comes later and must
be able to share the file format and the drawing logic, so build 1 keeps the two apart (see 9).

Read first: `docs/OCTOVIC.md` (registers, bitmap layer, blitter, sprites, turned and sized),
`docs/OCTOVIC_MEMORY.md` (what costs DDR3 time on real hardware), `docs/OCTOOS.md` (keys, mailbox,
start screen), `tools/octoos/octocode/` (an app done the same way: build.sh, how it starts and quits).

## 1. Files and names

| path | what |
|---|---|
| `tools/octopaint/octopaint.asm` | the program (ACME, `-f cbm`), loads at `$0801` with a `10 SYS2061` stub |
| `tools/octopaint/palette.inc` | the default 256-colour palette (generated by `mkpal.py`, checked in) |
| `tools/octopaint/mkpal.py` | makes `palette.inc` |
| `tools/octopaint/mkoct.py` | PC tool: PNG/BMP -> `.OCT` and `.OCT` -> PNG (the same format the 6502 writes; the Windows version's starting point) |
| `tools/octopaint/build.sh` | builds `OCTOPAINT.PRG` and `OctoPaint Disk build N.d64` |
| `tools/octopaint/README.md` | how to build and test |
| `docs/OCTOPAINT.md` | the user manual and the `.OCT` format (exact, byte by byte) |

The build number N is in every file name a user gets (`OCTOPAINT build N.zip`, the disk). The title
bar shows `OCTOPAINT BUILD N`.

## 2. Starting and quitting

1. Start: switch OctoVIC on (`$D03F` = `$4F`, `$38`), read `$D61E` = `$8C` and `$D61F` >= 2. If not:
   print `OCTOPAINT NEEDS THE OCTOPHONIC 64 (OCTOVIC 2+)` on the normal screen and return to BASIC.
2. Turbo on (`$D030` = 1), interrupts set up from a raster IRQ (frame timer for the pointer and
   keyboard, as the other demos do). Keep a LATE counter check (`$D6A0`) in the debug overlay (key `D`).
3. Quit: `F7` asks `QUIT? Y/N`. Yes: undo every OctoVIC setting (CTRL 0, layers off, sprites 0,
   copper off, IRQEN 0), restore the KERNAL IRQ, `$D030` = 0, VIC normal, clear screen, `JMP ($A002)`
   (BASIC warm start - back at READY with the start screen's normal state).

## 3. Screen layout

- **The canvas** is OctoVIC **layer 0, BITMAP, 256 colours** (LCTRL b0 b1 b3), map width code 1
  (512 pixels wide), map height code 0 (256 tall). The picture is **320 x 200** at the top-left of
  that bitmap; columns 320-511 and rows 200-255 are never shown at zoom 1 and stay colour 0.
  A pixel's VRAM byte: `CANVAS + y*512 + x`. Pixel 0 is see-through: the backdrop (PALSEL 2) shows,
  set to black, so colour 0 looks black and is "empty".
- **The UI** (toolbar) is a band at the bottom, 320 x 24 pixels, on **layer 1, BITMAP, 256 colours**
  (its own VRAM picture, drawn with the blitter's FILL and COPY0), plus the **VIC-II text** for
  labels: VIC in front (CTRL b2 clear) with KEYEN and KEY = the VIC background colour, so only the
  letters show over OctoVIC. Rows 22-24 of the VIC screen are the toolbar's text; rows 0-21 are
  empty (see-through) so the canvas is clear.
- `TAB` hides the toolbar (layer 1 off, VIC rows cleared): the canvas is then the full screen.
- **The pointer** is OctoVIC **sprite 0**, 16 x 16, 256 colours, priority 0, a white arrow with a
  black edge (drawn in the source as data). Tools that need it show a second sprite (1) as a
  crosshair or the brush outline.

Toolbar contents (left to right): current colour swatch (16 x 16) with its number; 32 palette
swatches (8 x 8 each, two rows of 16) showing a window of the palette (`<` `>` move the window by
32); the tool name; brush size; zoom; `F7 QUIT`.

## 4. VRAM map (bytes)

| address | size | what |
|---|---|---|
| `$000000` | 128 KB | the canvas (512 x 256) |
| `$020000` | 128 KB | undo copy of the canvas |
| `$040000` | 16 KB | the toolbar bitmap (layer 1: 512 x 32, only 320 x 24 used; layer 1 map height code 0 = 256 rows: give it a 512 x 256 area at `$040000`, 128 KB, mostly unused) |
| `$060000` | 4 KB | sprite graphics (SPRGFX) |
| `$061000` | 1 KB | sprite table (SATBASE) |
| `$070000` | 64 KB | spare: clipboard / brush stamp (build 2) |

Use VINC = 1 and VDATA for single pixels; the blitter for anything bigger than a few pixels.

## 5. Input

All three work at once:

- **Mouse**: a 1351 in **port 1** (the core's OSD option `Pot 1/2: Mouse`; the user sets it, the
  manual says how). Read POTX/POTY (`$D419`/`$D41A`) with port 1 selected on CIA 1 (`$DC00` b6-7),
  the standard 1351 delta method (6 bits, signed difference, ignore the noise bit); left button =
  joystick fire bit, right button = joystick up bit. Pointer speed 1:1 with screen pixels.
- **Joystick** in **port 2 and port 1**: moves the pointer 1 pixel a frame, 4 with fire held for
  more than 0.5 s (fire alone tapped = click). Pointer movement must not draw until fire is used as
  the "pen down" (see tools).
- **Keyboard**: cursor keys move the pointer 1 pixel (SHIFT: 8); `RETURN` = left button (pen down
  while held); `SPACE` = right button.

Key map (also printed in the manual and on a help page, key `H`):

| key | does |
|---|---|
| `P` | pencil (1 pixel) |
| `B` | brush (size 1, 2, 4, 8; square) |
| `1` `2` `3` `4` | brush size 1, 2, 4, 8 |
| `L` | line (press at the start, release at the end; rubber band shown with sprite 1 as the end mark, line drawn on release) |
| `R` | rectangle outline; `SHIFT+R` filled |
| `C` | circle outline (centre, then radius); `SHIFT+C` filled |
| `F` | flood fill (build 1: 4-way, same-colour, scanline fill reading VRAM through VDATA) |
| `K` | pick the colour under the pointer (VDATA read: set VADDR, wait 2 us, read) |
| `+` `-` | colour number up / down; `<` `>` palette window |
| `E` | edit the current colour: R G B each 0-255, keys `Q/A W/S E/D` up/down by 4 (SHIFT by 1), shown live on the swatch and in numbers; `RETURN` keeps, `RUN/STOP` puts it back |
| `U` | undo (one level) |
| `Z` | zoom 1x / 2x / 4x around the pointer (layer 0 TURNED AND SIZED: DUX = DVY = 1/zoom in 16.16, U0/V0 to keep the pointer's canvas pixel under the pointer); at 2x/4x the arrow keys / joystick near the edge pan |
| `G` | grid at 4x zoom (layer 1 not used for it - draw the grid with sprites or skip in build 1; optional) |
| `TAB` | hide / show the toolbar |
| `N` | new picture (asks `CLEAR? Y/N`; clears the canvas to colour 0 with the blitter) |
| `S` | save (asks the name, max 12 letters) |
| `O` | open (asks the name) |
| `I` | import a Koala picture (`.KLA`, PRG type, 10003 bytes) |
| `H` | help page (VIC text, full screen, any key back) |
| `D` | debug overlay on/off (LATE, LATETOTAL, free RAM, pointer x y) |
| `F7` | quit (asks) |

Drawing tools draw in the **current colour** with the left button; the right button draws in
**colour 0** (rubber). Before each stroke (button down) copy the canvas to the undo copy with the
blitter COPY (320 x 200, rows 512 apart) and wait for it.

## 6. How each tool draws (exact)

- **Pencil / brush**: on each frame the button is held, draw from the last point to this point
  (blitter LINE for size 1; for bigger sizes stamp a FILL square of the brush size every pixel along
  the line - the 6502 steps the line with Bresenham, one FILL per step, waiting for the blitter).
  Clip to 0..319, 0..199.
- **Line**: blitter LINE, BDST = canvas, BDSTR = 512, BW = 320, BH = 200 (the blitter clips).
- **Rectangle**: 4 LINEs; filled = one FILL.
- **Circle**: midpoint circle on the 6502 using the maths unit for squares; outline plots with
  VDATA; filled = a FILL row (1 pixel high) per y.
- **Flood fill**: scanline algorithm with a stack in C64 RAM (max 1024 entries; if it fills up,
  stop and show `FILL TOO BIG`). Read pixels with VDATA (VINC = 1, reading a row left to right is
  fast), write runs with FILL rows. Must finish a 320 x 200 empty canvas in under 10 seconds in the
  emulator; measure it and write the time in the report.
- **Colour pick**: VDATA read at the pointer's canvas pixel.

Pixels drawn during the visible picture are fine (memory build), but keep blits small and never
run the blitter flat out across the whole frame for no reason (see OCTOVIC_MEMORY.md).

## 7. The default palette (`mkpal.py`)

- 0: black (see-through on the canvas, shown black). 1-15: a C64-like set of colours chosen by
  `mkpal.py` from its own RGB values (write them out in the script; do not copy any emulator's or
  other project's palette table). 16-255: 15 hue ramps of 16 steps, dark to light, then a 16-step grey
  ramp - generated in HSV in the script. Write the table as `!byte r,g,b` lines.
- Loaded into OctoVIC's main palette (PALSEL 0) at start; the toolbar uses only palette entries, so
  if the user edits a colour the toolbar uses, it changes too - accept that, it's a paint program.

## 8. Files: the `.OCT` format and the disk

Saved to and loaded from **drive 8** through the KERNAL (OPEN / CHROUT / CHRIN / CLOSE, SEQ file
`NAME.OCT,S,W` / `,S,R`), streaming through VDATA (VINC = 1) - no copy of the picture in C64 RAM.

**`.OCT` version 1, byte by byte:**

| offset | bytes | value |
|---|---|---|
| 0 | 4 | `OCT1` (ASCII) |
| 4 | 2 | width, little endian (320) |
| 6 | 2 | height (200) |
| 8 | 1 | bits per pixel: 8 |
| 9 | 1 | packing: 0 none, 1 run-length (below) |
| 10 | 768 | palette: 256 x (R, G, B) |
| 778 | ... | pixels, row 0 first, left to right, packed |

Run-length packing: a control byte n. n = 0-127: n+1 literal bytes follow. n = 128-255: the next
byte is repeated n-125 times (3-130). Rows are not separate: the stream is the whole picture.
`mkoct.py` and the 6502 must produce byte-identical files for the same picture (test it).

**The no-disk hang (must handle).** On the real MiSTer, with no disk in drive 8, a disk command
can wait for ever (OCTOCODE build 3 hung at start like this). So: before every save, open or import,
show `DISK IN DRIVE 8? Y/N` - `N` cancels with no disk access at all. Then read the error channel
(`OPEN 15,8,15`) and show the drive's message if it isn't `00`. Never touch the drive at start-up.

Progress: a bar on VIC row 21 while saving / loading (bytes done of total), and the result
(`SAVED NAME.OCT 23,456 BYTES` / the drive's error).

**Koala import (`I`)**: the standard 10003-byte layout (2 load-address bytes, 8000 bitmap, 1000
screen, 1000 colour, 1 background). Each 4 x 8 multicolour cell decodes to 2-wide pixels (a 160 x
200 picture doubled across to 320 x 200): C64 colour c -> palette entry c (0-15), black (0) is
entry 0 (see-through, shown black). Undo before import.

## 9. Kept apart for the Windows version

Lay the source out as: `platform` (OctoVIC registers, input, KERNAL disk I/O, the toolbar) and
`paint` (the tools' maths: Bresenham, circle, fill, run-length packing) - the `paint` routines take
coordinates and colours in zero page and call three platform hooks: `plot`, `fillrect`, `readpixel`.
A comment block at the top lists those hooks. `mkoct.py` implements the same run-length packing in
Python; the Windows version will start from it and the format doc.

## 10. Disk and package

`build.sh` makes:
- `OCTOPAINT.PRG`
- `OctoPaint Disk build N.d64`: OCTOPAINT first (so `LOAD"*",8,1` + `RUN` starts it), then two
  example pictures made by `mkoct.py` from pictures the script draws itself (an original test card
  with colour bars and gradients, and a 256-colour palette chart) - no outside art.
- `OCTOPAINT build N.zip`: the PRG, the d64, `How to use.txt` (from docs/OCTOPAINT.md, plain text),
  including how to put it on the MiSTer with FileZilla (SFTP to the MiSTer's IP, user `root`,
  password `1` unless changed; copy into `/media/fat/games/C64/Tools/`).

## 11. Testing (feedback loops - required)

Use the headless emulator harness in the session scratchpad (`emu1541/rt`, `k6/emu6.sh`, the
recorder scripts in `showcase/`), keyboard-scripted (the pointer is drivable by cursor keys and
RETURN for exactly this reason). For each step below: run, dump frames, **look at the screenshots**
(not just numbers), and fix before going on.

1. Starts, shows the toolbar and pointer, LATE = 0, F7 + Y returns to READY cleanly (start screen
   works afterwards).
2. Pencil, brush 1/2/4/8, line, rect, filled rect, circle, filled circle, fill, pick, rubber, undo,
   zoom 1/2/4 with pan, TAB, palette window, colour edit - one scripted run each, a screenshot each.
3. Save to a blank d64, quit, restart, open: VRAM checksum of 320 x 200 identical. Also: the saved
   `.OCT` extracted with `c1541` equals `mkoct.py`'s packing of the same pixels.
4. `DISK IN DRIVE 8?` -> N: no drive access (the harness can tell: no IEC traffic / no drive LED).
5. Koala import of a Koala file that the test makes itself (random but valid data) - no crash, plausible picture.
6. Flood fill time on an empty canvas, and on a checkerboard (worst case): report both.
7. A 30-second MP4 of a scripted drawing session (pointer moving, tools changing, a save), for Neal.

## 12. Rules

- 6502 only, ACME. No Commodore ROM code copied. Original art only.
- Commit as **Mong00se** on `octophonic-v1.1`, small commits, message lines plain English. Do not
  push releases; do not change the core, Main, or the SD-card image recipe in build 1.
- Do not touch Neal's PC or MiSTer. The finished zip and MP4 go to the session scratchpad
  `octopaint/` folder.
- If something in this spec turns out to be impossible or much slower than expected on OctoVIC,
  stop and say so in the report instead of quietly changing the design.
